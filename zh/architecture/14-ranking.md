# 推荐系统架构（14）：精排与 Prediction Server，千级候选的毫秒级打分引擎

**太长不看版**

召回阶段从海量内容池中筛选出约 1000 条候选条目，精排阶段对这 1000 个内容进行精细化打分，排序然后选出 200 ~ 300 进行重排。精排阶段模型比召回复杂得多，计算成本显著增加，因此需要独立的高性能推理服务，即 Prediction Server。

Prediction Server 是一个无状态的模型推理服务，内部主要模块有：API 层、特征处理、模型管理、推理引擎、结果处理等。它支持多模型共存、热更新、Batch 推理。Prediction Server 由 Realtime Engine 调用，成为推荐链路中最重要的环节之一。

本文从精排定位、模型体系回顾、Prediction Server 架构、性能优化、多目标融合、高可用治理、新模型上线流程等方面，系统介绍这套千级候选的毫秒级打分体系。

## 1. 精排在推荐链路中的定位

### 1.1 从召回到精排

上篇文章展示了推荐系统信息筛选漏斗：海量内容池 -> 召回（约 1000 条候选）-> 精排（Top 200~300）-> 重排，到最终展示几十条。精排位于这个漏斗中第二层，负责把 1000 条候选进行精细化打分，然后筛选头部 200 多条进行重排，最后返回。

召回阶段因为要从海量的内容池中筛选候选集，只能用轻量模型进行打分。到了精排阶段，候选一般只有千级别，需要计算的规模大大缩减，因此可以用更复杂的模型以及更丰富的特征做精细化打分。

### 1.2 精排与召回的区别

精排和召回阶段，可以从三个维度进行对比：

- 目标不同。召回要从海量内容中尽可能把用户可能感兴趣的内容找到，追求覆盖率；而精排是从少量候选中把最符合用户兴趣的内容排在前面，追求“排得准”。

- 计算规模不同。召回数据来源是百万乃至亿级内容，只能用索引加速查找、用轻量模型打分；精排的数据来源只有千级候选，可以用精细模型（多目标 DNN、序列模型），单条计算量变大但总体可控。

- 特征丰富度不同。召回通常只用用户侧聚合特征和内容侧基础特征；精排可以使用交叉特征、实时行为序列特征、上下文特征等更丰富的组合。

### 1.3 粗排和精排

当召回计算出来的候选集合比较大（数千到上万）时，一般会在召回和精排之间增加一层粗排，用比精排轻量但比召回重的模型将候选从数千压缩到数百。本文介绍的系统召回阶段只返回 1000 条，没有设计独立的粗排层。

精排阶段是对召回或者粗排计算出来的候选集，用最复杂的模型做逐条精准打分，现代推荐系统一般都是针对每条内容输出多目标预估值，然后综合排序取前 200 ~ 300。

## 2. 精排模型体系

> 本章只做简要回顾，算法原理参考第2篇，特征工程参考第3篇，模型训练参考第9篇。

### 2.1 精排模型的工程演进

精排模型经历了如下演进：

- **LR 时代**：线性模型，特征工程为主，推理极快、可解释性强，但表达能力有限。
- **GBDT 时代**：树模型自动学习特征交叉（XGBoost/LightGBM），大幅减少人工特征工程，推理仍很快，但高维稀疏特征处理能力有限。
- **深度学习时代**：主要使用深度学习模型（Wide&Deep、DeepFM、DIN 等），Embedding 自动学习高维稀疏特征，表达能力大幅提升。但推理成本也显著增加，需要专门推理服务支撑。

从 DNN 时代起，推荐算法的目标从之前的单一 CTR 优化，慢慢演进到多目标联合优化（MMOE、PLE、ESMM 等）。也即是一个模型，可以同时输出 CTR、停留时长、点赞率、收藏率等多个预估值。这种多目标输出能更好的对用户体验进行综合优化。多目标优化模型的表达能力增强，对应的在线推理基础设施也要进行相应升级来支持。

### 2.2 多目标精排模型

**为什么需要多目标**。单一 CTR 优化会导致标题党泛滥——模型只关心用户会不会点，不关心点了之后体验好不好。用户体验是综合的：点击但马上退出是负体验，点击且长时间停留是正体验，点赞收藏评论是深度正体验。

**常见结构**（不展开算法原理，侧重工程选型）：

- **Shared Bottom**：底层共享，顶层每个目标一个 Tower。最简单，但目标差异大时存在负迁移。
- **MMOE**：多个 Expert 共享，每个目标有独立 Gate 动态决定 Expert 组合。缓解负迁移，工业界常用。
- **PLE**：MMOE 进阶版，Expert 分为共享和目标专属，效果更好但复杂度更高。
- **ESMM**：解决 CVR 预估的样本选择偏差和数据稀疏问题，通过 CTR × CVR = CTCVR 在全样本空间训练。

**工程考量**。目标数量不是越多越好，相关性强的适合联合训练，弱的分开建模效果可能更好；多目标推理成本比单目标高，需在 Prediction Server 中优化；离线评估需综合看所有目标指标，不能只看单一 AUC。

### 2.3 精排特征体系

精排特征分为四类（特征工程原理参考第3篇，此处侧重精排特有使用方式）：

- **用户特征**：基础属性、兴趣画像（长期/短期标签、兴趣 Embedding，参考第8篇）、行为序列（最近点击/浏览序列，用于 DIN/SIM 注意力建模）、统计特征（历史 CTR、平均停留时长）。
- **内容特征**：基础属性（分类、关键词、实体、作者，参考第5篇）、内容 Embedding、统计特征（历史曝光量、点击率、热度分）、质量特征（内容质量分、低俗检测分）。
- **交叉特征**：用户-内容交叉（用户对该分类/作者/关键词的历史 CTR）、召回来源特征（该内容被哪些召回源召回、各源打分，参考第13篇 3.2 节）。召回来源特征是精排特有的——同一内容从兴趣标签召回和从热门召回，用户点击意愿可能不同。
- **上下文特征**：请求时间、时间段、场景（首页/频道/搜索）、页面位置、实时热点信号。

**工程原则**。特征一致性——在线推理特征必须和离线训练特征计算逻辑一致（参考第9篇 Feature Log 的作用），这是精排效果的生命线；特征时效性——实时特征和离线特征区分管理；特征重要性——通过 SHAP、增益贡献度筛选有效特征，避免冗余增加推理成本。

### 2.4 模型输入输出结构

**输入**。一次请求约 1000 个候选，用户特征和上下文特征在请求内只计算一次，和每个 Item 的内容特征、交叉特征拼接形成 Batch 输入（用户/上下文特征在 Batch 内广播）。

**输出**。多目标模型输出每个 Item 的多个目标预估值：

```JSON
{ "item_id": "D12345", "predictions": { "ctr": 0.083, "stay_duration": 47.5, "like_rate": 0.012 } }
```

这些原始预估值传给多目标融合模块计算最终排序分。融合放在 Prediction Server 还是 Realtime Engine，第 5 章详细讨论。

## 3. Prediction Server 架构设计

### 3.1 为什么需要独立的 Prediction Server

精排推理可以内嵌在 Realtime Engine 中（第12篇的 PredictionRankingProcessor 就是在引擎内部调用排序逻辑），但工业级系统通常拆分为独立服务，原因：

**计算资源隔离**。模型推理是 CPU/GPU 密集型操作，和业务逻辑（召回调度、特征获取、重排规则）同进程会互相影响。推理占满 CPU 时可能导致业务线程饥饿，整条链路延迟受影响。独立部署后可单独扩缩容。

**技术栈解耦**。模型推理由 C++/Python + 推理引擎（ONNX Runtime、TensorRT）实现，追求极致性能；业务服务用 Java/Go，追求开发效率。独立服务可各自选最合适的技术栈。

**多模型统一管理**。推荐系统有多个模型（精排、粗排、召回、内容理解、校准等），统一的 Prediction Server 集中管理模型加载、版本切换、A/B Test，避免每个业务服务各自维护一套。

**独立迭代节奏**。模型更新频繁（天级甚至小时级），业务逻辑更新相对慢。独立部署后模型更新只需热更新 Prediction Server，不影响业务服务。

架构定位：Prediction Server 是**无状态的模型推理服务**，接收特征输入，返回模型打分结果。模型文件从 Model Registry 拉取。

### 3.2 服务整体架构

```
                    ┌─────────────────────────────────────┐
                    │         Prediction Server            │
  请求入口 ────────►│  API Layer (gRPC/HTTP)             │
                    │  Feature Processor                   │
                    │    - 特征拼接、类型转换、缺失值处理   │
                    │    - 准备排序侧 Feature Log 数据      │
                    │  Model Manager                       │
                    │    - 模型加载/卸载、热更新、多版本共存 │
                    │  Inference Engine                    │
                    │    - Batch 调度、推理后端执行          │
                    │  Result Processor                    │
                    │    - 结果解析、概率校准、多目标封装    │
                    └─────────────────────────────────────┘
```

各模块职责：

- **API Layer**：接收推理请求，解析模型名称、版本、特征数据，路由到对应模型实例。高并发场景一般用 gRPC。
- **Feature Processor**：特征预处理（类型转换、缺失值填充、特征校验），同时准备排序侧 Feature Log 数据随响应返回。注意不是自己写日志，而是准备好数据返回，由 Realtime Engine 拼接完整日志后写入，3.4 节详述。
- **Model Manager**：管理模型生命周期（加载、热更新、多版本共存、内存管理），最复杂的模块之一，3.3 节展开。
- **Inference Engine**：核心推理模块，接收 Tensor 后做 Batch 调度，交给推理后端执行，返回结果 Tensor。Batch 调度直接影响吞吐和延迟，第 4 章详细讨论。
- **Result Processor**：模型输出后处理（概率校准、多目标分数封装），校准参数从模型元数据获取。

### 3.3 模型管理与加载

**模型文件格式**。不同框架产出格式不同（TensorFlow SavedModel、PyTorch TorchScript/ONNX、LightGBM 原生文件）。工程实践中通常统一转 ONNX 格式，用 ONNX Runtime 作统一推理后端，一次转换多后端可跑（CPU、GPU、ARM），减少多框架维护成本。

**加载策略**。启动加载——服务启动时加载全量模型，完成后接收请求，缺点是启动慢，大模型需几分钟，扩容时新实例不能快速接管。预热加载——启动后异步加载，加载完成前拒绝请求或返回降级，配合 K8s readiness probe，推荐使用。

**模型热更新**。模型更新是高频操作（天级/小时级），不能每次重启。热更新机制：

1. Model Manager 监听 Model Registry 版本变更（或定时轮询）。
2. 异步下载新模型到本地。
3. 内存中加载新模型，旧模型继续服务。
4. 新模型加载完成后，原子切换流量到新模型（修改指针，后续请求走新模型）。
5. 确认无异常后卸载旧模型释放内存。

双版本机制保证更新不中断，出问题可快速回滚。关键是原子切换，不能出现部分请求走新模型、部分走旧模型的中间状态（A/B Test 场景除外，那是有意为之）。

热更新注意：新旧模型同时存在时占用额外内存，需确保实例有余量；加载过程 CPU 占用升高可能影响正在进行的推理，建议低峰期执行或对加载线程限速。

**多模型共存**。一个实例通常同时加载多个模型：不同场景的精排模型（首页、频道、搜索）、同一模型的多版本（A/B Test 基线和实验共存）、辅助模型（粗排、内容质量、校准）。需管理内存占用，模型权重（几十 MB 到几 GB）和 Embedding 表（可能几十 GB）是主要消耗。必要时按模型类型拆分到不同集群。

### 3.4 特征拼接与校验

**特征拼接**。Realtime Engine 传入的结构化 Key-Value 特征需转换为模型输入 Tensor：

- 稀疏特征（ID 类）：查 Embedding 表转稠密向量。Embedding 表可内置在模型文件中，也可外置到参数服务器。推荐模型 Embedding 表通常占体积 80% 以上，外置可减小模型文件但增加一次网络查询。
- 稠密特征（统计值）：直接转浮点 Tensor，可能需归一化（和训练时归一化参数一致，参数保存在模型元数据中）。
- 序列特征：按时间排列，做 Padding/Masking，截断到训练时最大长度。
- 多值特征：转多热向量或 Bag Embedding。

**特征校验**。特征缺失用默认值填充（和训练时缺失值处理一致）；类型错误尝试转换或用默认值；值域异常（停留时长为负、CTR 超 1）做截断或标记告警；通过 PSI 监控在线特征分布和训练时差异，PSI > 0.25 通常认为分布显著偏移，需排查。

**Feature Log 准备**。每次推理，Prediction Server 准备排序侧 Feature Log 数据（request_id、模型版本、每个候选特征快照、模型原始输出），作为响应一部分返回给 Realtime Engine。

为什么不让 Prediction Server 自己写日志？因为完整 Feature Log 还包含召回阶段信息（召回源、召回分数、召回耗时），由 Realtime Engine 拼接召回侧和排序侧数据成完整日志，统一写入文件或 Kafka 更合适（参考第9篇 3.2 节）。Prediction Server 只负责准备排序部分，职责更单一。

### 3.5 推理执行引擎

推理执行引擎是 Prediction Server 的核心，执行流程很简单：

```
接收 Tensor → Batch 调度 → 推理后端（Backend）执行 → 返回 Tensor
```

**推理后端选型**：

- **ONNX Runtime**：微软开源跨平台推理引擎，CPU/GPU 都有优化，工业界常用的统一后端。
- **TensorRT**：NVIDIA GPU 推理优化引擎，性能极致，但只支持 NVIDIA GPU，模型转换有兼容性问题。
- **TF Serving / TorchServe**：各自生态官方服务，功能完善但性能一般，适合快速验证。
- **自研推理引擎**：大公司针对推荐模型特点（大量 Embedding 查找、稀疏特征）深度优化。

对大多数团队，ONNX Runtime 是性价比最高的选择。Batch 调度是推理引擎最关键的环节，直接决定吞吐和延迟，第 4 章详细展开。

### 3.6 与上下游协作

**与 Realtime Engine 的协作流程**：

1. Realtime Engine 完成召回，获得约 1000 条候选。
2. 特征准备（两种设计见下文）。
3. 构造推理请求，指定模型名称和版本，发给 Prediction Server。
4. Prediction Server 执行推理，返回多目标预估值和排序侧 Feature Log 数据。
5. Realtime Engine 做多目标融合计算最终排序分，取 Top 200~300 交给重排；同时拼接完整 Feature Log 写入文件或 Kafka。

**特征获取的两种设计**：

**设计一（本文主设计）：Realtime Engine 获取全部特征，发送给 Prediction Server。**

Realtime Engine 从 Feature Server 批量获取用户、内容、交叉、上下文特征，随请求一起发给 Prediction Server。Prediction Server 只负责推理，不关心特征来源。

优点：特征获取和推理解耦，Prediction Server 轻量纯一；可复用召回阶段已获取的部分特征（用户画像、内容基础属性），减少重复查询；特征获取失败时 Realtime Engine 可直接降级，不浪费推理资源。

缺点：请求传输量较大（1000 候选特征可能几百 KB 到几 MB）；特征变更需同步修改 Realtime Engine。

**设计二：Realtime Engine 只发 Feature Name List，Prediction Server 自行获取特征。**

Realtime Engine 只告诉 Prediction Server 需要哪些特征和候选 Item ID，Prediction Server 内部从 Feature Server 获取。

优点：传输量小；特征依赖由 Prediction Server 管理，模型特征变更不影响调用方；可做特征预取和缓存优化。

缺点：与 Feature Server 耦合，特征获取耗时计入推理总耗时，Feature Server 抖动直接影响推理延迟；Realtime Engine 侧缓存无法复用。

实际也可混合：用户和上下文特征由 Realtime Engine 传入（复用缓存），内容和交叉特征由 Prediction Server 获取（减少传输量）。本文后续以设计一为主。

**与 Model Registry 的协作**。启动时拉取当前线上模型，运行时定期检查新版本触发热更新。模型元数据（特征列表、输入输出格式、校准参数）从 Model Registry 获取，用于特征校验和请求解析（设计二中 Feature Name List 可从元数据自动获取）。

## 4. 在线推理性能优化

### 4.1 推理性能的核心指标

- **延迟**：单次推理端到端耗时，关注 P99（决定用户体验下限），精排 P99 通常要求 20~50ms。
- **吞吐量**：单位时间处理的请求数或候选数（QPS/CPS），决定需要多少机器，直接影响成本。
- **资源利用率**：CPU/GPU 利用率、内存占用。高利用率意味低成本，但过高（CPU > 90%）会导致排队增多、P99 恶化。
- **性价比**：单次推理的计算资源成本，大规模系统的核心优化目标。

优化目标：在满足延迟 SLA 的前提下，最大化吞吐，最小化成本。四个指标有权衡——极致低延迟可能需降低 Batch 导致吞吐下降成本上升；高吞吐可能需增大 Batch 导致延迟上升。需根据业务场景找平衡点。

### 4.2 Batch 推理优化

Batch 推理是提升 GPU 利用率和吞吐最有效的手段，也是 Prediction Server 性能优化的核心。

**请求内 Batch**。一次请求的约 1000 个候选共享用户和上下文特征，组成 Batch 一次性输入模型。最基础的形式，每个请求内部完成。

**跨请求 Dynamic Batching**。更有效的方式是将多个用户请求的候选合并成更大 Batch：

```
请求 A：1000 候选 + 请求 B：800 候选 + 请求 C：900 候选
    ↓ 合并
大 Batch：2700 候选，一次推理
    ↓ 拆分
分别返回各请求结果
```

实现要点：请求进入队列后，等待固定时间窗口（5~10ms）或累积到最大 Batch 大小，满足任一条件开始推理；高优先级请求可插队或用更小时间窗口；等待时间 + 推理时间不能超过请求总超时，需动态调整——队列里已等了 8ms 就不能再等，立即开始。

**Batch 大小的权衡**。太小则 GPU 利用率低、吞吐上不去；太大则单次推理时间长、请求等待增加、P99 恶化。最优 Batch 大小需压测确定，通常 128~1024 之间（取决于模型大小和硬件）。压测时同时看吞吐和 P99，找到"P99 满足 SLA 前提下吞吐最大"的 Batch 大小。

**算子优化**。推荐模型高频算子可针对性优化：Embedding 查找用哈希表/缓存/分片加速；特征交叉（FM、DeepFM）用向量化、预计算加速；注意力机制（DIN、SIM）用 FlashAttention 优化。

### 4.3 模型优化技术

**模型量化**。将 FP32 参数转低精度（FP16、INT8、INT4），减少内存和计算量。

- FP16：精度损失极小，GPU 原生支持，速度提升 1.5~2 倍，最常用，几乎无副作用。
- INT8：精度损失较大，需校准数据集，速度提升 2~4 倍，适合对精度不敏感的场景。
- INT4：极致压缩，通常只用于 Embedding 表。

推荐模型 Embedding 表占内存 80% 以上，对 Embedding 做 INT8/INT4 量化可大幅减少内存且效果影响较小——Embedding 精度要求不如 MLP 权重高，少量损失对最终排序影响不大。

**模型剪枝**。移除不重要的参数。结构化剪枝（移除整个神经元/通道/层）可直接加速；非结构化剪枝需稀疏计算库支持。推荐模型 MLP 层宽度可通过剪枝压缩，但需重新训练或微调。

**知识蒸馏**。用大模型（教师）指导小模型（学生）训练，学生学习教师的输出分布，保持效果的同时大幅降低推理成本。教师是复杂多目标 DNN，效果好但慢；学生是轻量模型（浅层 LR、小 DNN），快但单独训练效果差。蒸馏时学生同时学习真实标签和教师的软标签。

蒸馏是工业界常用的"降本增效"手段，特别适合粗排模型——粗排需轻量但希望接近精排效果，用精排蒸馏粗排是常见做法。精排本身也可用蒸馏——用更大更复杂的模型蒸馏出稍小但效果接近的模型，降低推理成本。

### 4.4 硬件选型与缓存策略

**CPU vs GPU**。CPU 推理适合中小模型、低 QPS 场景，灵活、成本低、扩容方便，但大模型推理慢、吞吐有限。GPU 推理适合大模型、高 QPS 场景，并行计算强、Batch 推理吞吐高，但成本高、显存有限、运维复杂。

推荐场景选择：中等规模 DNN（几十 MB 到几百 MB，不含超大 Embedding），CPU 推理通常足够且成本更低——CPU 的灵活性在推荐场景很有价值，模型更新频繁，CPU 实例启动和热更新都比 GPU 快。模型很大（单模型几 GB 以上）或 QPS 很高（单集群几万 QPS）时，GPU 更有性价比。实际也可混合：基础精排用 CPU，复杂实验模型或大模型用 GPU，按类型拆分集群。

**缓存策略**：

- **特征缓存**：同一用户短时间多次请求（快速翻页），用户特征缓存 1~5 分钟；内容特征变化频率低，缓存 1 小时或更新时主动失效。
- **Embedding 缓存**：缓存热点 ID 的 Embedding 向量，LRU 替换。热点 ID（热门内容、活跃用户）访问频率很高，缓存命中率可做到 80% 以上。
- **推理结果缓存**：精排推理结果缓存价值有限（用户实时行为变化快，相同特征输入概率低），但内容理解模型（质量分、分类标签）的推理结果可缓存——内容特征相对稳定。

多级缓存：L1 进程内（最快、容量小）→ L2 本机共享/Redis（较快、容量中等）→ L3 Feature Server/参数服务器（较慢、容量大）。注意缓存一致性（特征更新及时失效）、穿透（空值缓存/布隆过滤器）、雪崩（随机化过期时间）。

## 5. 多目标融合与排序输出

### 5.1 多目标分数的业务含义

精排模型输出多个目标预估值，各对应不同业务含义：

- **CTR**：点击概率，反映内容吸引力和标题/封面质量。CTR 高说明吸引人，但不一定质量好。
- **停留时长**：点击后预计停留时间，反映内容质量和深度兴趣。停留时长高说明确实有价值。
- **完播率/阅读完成率**：看完概率，反映内容完整性和吸引力。
- **点赞/收藏/评论/转发率**：深度互动概率，反映内容价值和用户认可度。
- **负反馈率**：不感兴趣、举报、拉黑概率，反映内容负面风险。

不同场景各目标重要性不同：资讯类停留时长 > CTR > 互动率；短视频类完播率 > 停留时长 > CTR；电商类转化率 > CTR > 收藏率。融合目标：根据业务目标将多个预估值组合成最终排序分，使排在前面的内容综合体验最优。

### 5.2 融合放在哪里：Prediction Server vs Realtime Engine

多目标融合放在哪个服务执行，是架构设计问题。

**设计一：融合放在 Prediction Server。** Prediction Server 推理后直接执行融合，输出最终排序分。Realtime Engine 只需接收最终分数。

优点：Realtime Engine 更轻量；融合逻辑和模型绑定，模型更新时融合策略一起发布，版本管理清晰。

缺点：融合策略本质是业务策略，变化频繁（权重调整、公式变更、新增业务调整项），每次变化都需重新部署 Prediction Server——而推理服务应保持稳定，频繁部署影响稳定性。Prediction Server 职责变重，从纯推理变成"推理 + 业务策略"，违背单一职责。

**设计二：融合放在 Realtime Engine（本文采用）。** Prediction Server 只负责推理，输出各目标原始预估值（prediction）。Realtime Engine 收到后执行融合计算最终排序分（objective）。

优点：**模型负责 prediction，业务层负责 objective**，职责分离清晰。融合策略变化只需修改 Realtime Engine 配置或代码，不需重新部署 Prediction Server，推理服务保持稳定。融合逻辑可灵活做 A/B Test——不同实验组用不同融合公式，只需 Realtime Engine 侧配置，Prediction Server 无需改动。

缺点：Realtime Engine 需知道各目标含义和融合逻辑，职责更重；响应数据量略大（返回所有目标预估值而非只返回最终分数）。但增加可控——1000 候选，每候选 5 个目标值，也就 5000 个浮点数，几十 KB。

本文采用设计二，这也是工业界更常见的做法。两者边界很清晰：Prediction Server 输出"这个内容被点击的概率是多少、预计停留多久"，Realtime Engine 决定"基于这些预估值，这个内容应该排在第几位"。

### 5.3 加权融合策略

**线性加权**。`final_score = w1 × ctr + w2 × stay_duration + w3 × like_rate + ...`。简单、可解释、权重调整方便，改配置即生效。缺点是各目标量纲不同（CTR 是 0~1，停留时长是几十秒），需先归一化（除以历史均值，或用 sigmoid/对数变换压缩量级）。适合初期快速上线。

**乘积融合**。`final_score = ctr × stay_duration × (1 + like_rate) × ...`。符合用户体验直觉——点击且停留长才是好内容，任一目标低都拉低总分。一个 CTR 高但停留短的标题党，乘积融合会给低分，线性加权可能因 CTR 权重高而排前面。缺点是某目标为 0 时总分变 0，需加平滑项（如 ctr + 0.001）。电商场景 pCTR × pCVR = pCTCVR 是典型应用。

**公式化融合**。`final_score = ctr^α × stay_duration^β × exp(γ × like_rate) × quality_boost`。α、β、γ 是指数权重，通过离线评估和线上 A/B Test 调优。指数权重比线性更灵活——CTR 指数设 0.5 相当于开根号降低影响（避免标题党），停留时长指数设 1.5 放大影响。quality_boost 是业务调整项（内容质量加权、新内容扶持、作者权重），变化频繁，放在 Realtime Engine 融合公式里非常合适，改配置即生效。公式化融合兼顾灵活性和可解释性，是工业界常用方式，我们线上用的就是类似公式。

**模型化融合（Learning to Rank）**。用轻量模型（GBDT、小 DNN）学习多目标分数到最终排序分的映射，输入是精排各目标预估值 + 部分业务特征，输出最终排序分，训练标签是用户综合反馈。优点是可学习目标间非线性关系，效果通常优于人工公式；缺点是可解释性差、出问题不好排查、需额外模型训练和维护。大多数团队到公式化融合就够用了。

融合策略选择：初期用线性加权或乘积快速上线；后期根据业务复杂度演进到公式化或模型化。

### 5.4 概率校准与输出结构

**概率校准**。模型输出的预估值通常不是准确概率，而是排序用的相对分数——训练优化的是 AUC（排序能力），不是概率准确性。AUC 只关心正负样本相对顺序，不关心绝对值。因此模型输出 CTR 可能整体偏高或偏低，或在不同区间偏差不一致。

在多目标融合（不同目标概率需可比）、广告竞价（CTR 直接影响出价）、业务分析等场景需要准确概率。校准方法：

- **Platt Scaling**：输出后加 Sigmoid，学习两个参数（a, b）映射到准确概率。`calibrated_p = sigmoid(a × logit(p) + b)`，适用于二分类，简单有效。
- **Isotonic Regression**：学习单调非递减映射，更灵活但需更多数据、易过拟合。
- **分箱校准**：按输出分位数分箱，每箱统计实际正样本比例作为校准值。简单直观。

工程实现：校准模型离线训练，参数作为模型一部分存 Model Registry，Prediction Server 的 Result Processor 推理后自动应用。校准后验证校准曲线、Brier Score、ECE。注意校准可能轻微降低 AUC（改变了分数相对关系），需在排序能力和概率准确性间权衡。

**精排输出结构**。Prediction Server 返回每个 Item 的原始预估值（raw_predictions）和校准后预估值（calibrated_predictions）。Realtime Engine 基于校准后的值做融合计算最终排序分（final_score），按分数排序取 Top 200~300 交给重排（参考第12篇 5.1 节）。

召回来源信息（recall_sources、recall_scores）从召回阶段透传，精排和重排都可参考——比如重排时对同一召回源过度集中的内容做打散。这些信息也写入 Feature Log，用于离线分析和问题排查。

## 6. 高可用与工程治理

### 6.1 超时、熔断与降级

**超时控制**。Realtime Engine 调用 Prediction Server 时设明确超时（如 30ms），超时后不再等待直接降级。Prediction Server 内部也设推理超时，超过后中止当前 Batch 返回已完成部分或错误。超时时间根据模型大小、硬件、业务 SLA 综合确定，压测找最优——太短导致大量超时降级，太长拖垮整条链路延迟。

**熔断**。Prediction Server 错误率或延迟超阈值时，Realtime Engine 侧自动熔断，暂停调用直接降级。熔断条件：最近 N 次请求错误率超 X% 或 P99 延迟超 Y ms；恢复：每隔 Z 秒放少量请求探测，成功后关闭。可用 Sentinel/Hystrix 或自研滑动窗口。

熔断意义在于防止级联故障——Prediction Server 响应变慢时，Realtime Engine 不断发请求等待会导致线程池占满，进而影响其他业务逻辑，最终全链路雪崩。熔断就是在 Prediction Server 出问题时快速切断，保护 Realtime Engine。

**降级策略**（Prediction Server 不可用时 Realtime Engine 侧执行）：

- **一级降级**：用召回分数排序。放弃精排，直接用召回原始分数（向量相似度、标签匹配度等）排序。效果下降但保证有结果。
- **二级降级**：用轻量模型。Realtime Engine 内置极轻量排序模型（LR、简单公式），本地快速计算。比召回分数排序效果好。我们线上内置了简单 LR 作兜底，特征用最基础几个（用户历史 CTR、内容热度、召回分数），推理不到 1ms。
- **三级降级**：返回预缓存结果。连轻量模型都不可用时，返回预计算热门列表或用户缓存推荐结果。最后兜底，保证用户能看到内容。

降级触发条件和优先级在 Realtime Engine 配置（参考第12篇多级容灾）。监控统计降级触发率——突然升高说明 Prediction Server 出问题了，需立即排查。

### 6.2 模型版本、热更新与回滚

**版本管理**。每个模型有唯一版本号，Model Registry 管理生命周期状态（待上线、A/B Test 中、全量上线、下线、归档）。Prediction Server 按配置加载指定版本，支持同一模型多版本同时在线——A/B Test 中基线和实验共存，按请求参数路由。

**热更新**。机制在 3.3 节详述：监听版本变更 → 异步下载 → 内存加载新模型（旧模型继续服务）→ 原子切换流量 → 确认无异常后卸载旧模型。双版本保证更新不中断。注意新旧共存时占用额外内存，需确保余量；加载时 CPU 升高可能影响推理，建议低峰期或限速加载。

**回滚**。新模型出问题（系统指标异常、业务指标下降、打分异常）需快速回滚。

最快速的是**流量切换回滚**——新旧模型同时在线，只需在 Traffic Splitter 或 Realtime Engine 配置中将新模型流量切回旧模型，秒级生效。这也是热更新时不立即卸载旧模型的原因——保留旧模型随时可快速回滚。

如果新模型有 bug 需修复，在 Model Registry 中将基线版本指回旧版本，Prediction Server 热更新后生效。问题出在融合公式、特征配置等非模型部分时，回滚 Realtime Engine 配置即可。

回滚后需分析原因：模型训练问题（样本脏、标签错）、特征问题（在线训练不一致）、推理性能问题（新模型太慢）、业务场景变化（热点事件导致分布偏移）。找到问题修复后重新走上线流程。不允许未定位问题就重新上线同一模型——否则同样问题会再次出现。

### 6.3 Shadow / A/B Test 支持

**A/B Test 支持**。Prediction Server 同时加载基线和实验模型，根据请求中的 model_version 路由到不同版本。基线和实验共享硬件资源但内存独立加载。流量比例由 Traffic Splitter 控制（参考第11篇），Prediction Server 只负责按版本路由——它不关心某个模型是基线还是实验，只需要根据版本号找到对应实例执行推理。

精排层实验和召回层、重排层实验正交（参考第13篇 4.3 节）——同一请求可能同时命中召回层和精排层实验，Prediction Server 只处理精排层版本选择。多层实验框架详细设计在第15篇。

Prediction Server 记录每个版本的调用量、延迟、错误率、打分分布（均值、分位数），用于排查异常——如果实验模型打分分布和基线差异巨大，可能是训练有问题或特征不一致。Feature Log 中记录模型版本，离线可按版本分析。

**Shadow 流量支持**。新模型上线前用 Shadow 流量做在线验证，发现离线评估发现不了的问题（特征不一致、推理性能、极端输入异常）。

Shadow 流量的复制和路由是 Traffic Splitter 的功能（参考第11篇），本节不重复。Prediction Server 侧需支持：

- **Shadow 请求识别**：请求携带 `shadow=true`、`shadow_model_version=xxx` 标记，识别后路由到对应实验模型。
- **结果不回传**：Shadow 推理结果不返回调用方（或返回空），只在内部记录，避免影响线上推荐。
- **资源隔离**：Shadow 请求用空闲资源执行，不抢占正常流量。通过独立线程池/GPU 流、低优先级调度、最大并发限制实现。资源紧张时优先丢弃 Shadow 请求——Shadow 验证重要，但不能影响线上用户。
- **对比数据记录**：记录 Shadow 和基线模型的打分分布差异、排序结果差异（Top K 重合率）、延迟对比，写入日志供离线分析。

Shadow 验证通过后（打分分布无异常、延迟满足 SLA、排序差异在预期范围内），新模型才进入小流量 A/B Test（参考第9篇 6.2 节 Pre-Deploy 校验）。

### 6.4 监控与特征一致性

**监控体系**分四个层面：

- **系统层**：QPS、延迟（P50/P99/P999）、错误率、超时率；CPU/内存/GPU/显存利用率；网络带宽、连接数。
- **模型层**：每个版本的调用量、延迟、错误率；打分分布（各目标均值、分位数）和历史基线对比——如果 CTR 预估值均值突然从 0.05 变 0.5，肯定有问题；模型加载状态（当前版本、加载时间、内存占用）；热更新事件。
- **特征层**：特征缺失率（突然升高说明上游 Feature Server 有问题）；特征分布 PSI（在线和训练差异，超阈值告警）；特征获取延迟（设计二中 Prediction Server 直接获取特征时监控）。
- **业务层**：精排后 Top K 内容分布（分类、热度、新旧比例）——如果全是热门内容可能模型有偏；精排和召回的排序一致性（无效召回率，参考第13篇 4.2 节）；降级触发率。

告警示例：错误率 > 1% 持续 1 分钟 → P1；P99 延迟 > 50ms 持续 3 分钟 → P2；特征缺失率 > 5% → P2；打分分布突变（均值偏移 > 20%）→ P2。

**特征一致性保障**。特征一致性是精排效果的生命线——在线推理特征和离线训练特征不一致，模型效果会严重下降。离线 AUC 提升但线上不升反降，最常见原因就是特征不一致。

风险点：计算逻辑不一致（在线离线用不同代码，如在线"最近7天"离线"最近168小时"，跨天结果不同）；时效性不一致（离线用 T 时刻快照，在线用实时特征，正常但差异过大说明逻辑可能变了）；定义不一致（同名特征取值范围/单位/编码不同，如在线用户等级 1~5 离线 0~4）；缺失处理不一致（在线用默认值，离线过滤缺失样本，导致分布不一致）。

保障措施：统一特征计算代码（在线离线复用同一套逻辑，从根源避免不一致）；Feature Log 校验（在线记录 Feature Log，离线训练用快照而非重新计算，参考第9篇 3.2 节）；特征版本管理（每个特征有版本号，定义变更时升级，训练和推理都绑定版本）；在线监控（PSI 监控分布差异，定期抽样对比在线离线取值）。

## 7. 一个新模型如何上线

一个精排新模型从训练完成到全量上线，经历以下流程：

```
Train → Offline Eval → Registry → Shadow → A/B Test → Ramp-up → Full Release → Monitor
```

下面逐个阶段说明，重点标注 Prediction Server 在各阶段承担的职责。

**Train（模型训练）**。离线系统基于样本训练新模型，产出模型文件。Prediction Server 不参与。训练流程参考第9篇。

**Offline Eval（离线评估）**。新模型在测试集上评估（AUC、GAUC、MSE 等，参考第9篇 5 节），达到预期（如 AUC 提升 > 0.1%）后进入下一阶段。同时做特征一致性检查，确认新模型使用的特征线上 Feature Server 都有且计算逻辑一致。Prediction Server 不参与。

离线评估是第一道门槛，但离线好不等于线上好——离线用历史数据，无法模拟用户看到推荐后的真实反应。所以还需 Shadow 和 A/B Test 在线验证。

**Registry（模型注册）**。模型注册到 Model Registry，标记"待上线"，包含元数据（特征列表、输入输出格式、依赖配置、离线评估报告、校准参数）。Prediction Server 此时可拉取元数据做合法性校验——文件大小是否正常、能否成功加载、输入输出格式是否符合约定。加载失败或格式不对直接打回。

**Shadow（Shadow 流量验证）**。Prediction Server 加载新模型到内存（与旧模型共存），Traffic Splitter 复制 1%~5% 线上流量做 Shadow 推理（流量复制参考第11篇，Prediction Server 侧支持参考 6.3 节）。新模型结果不返回用户，只记录对比数据。

Prediction Server 承担：加载新模型（与旧共存）、识别 Shadow 请求路由到新模型、用空闲资源执行（不影响正常流量）、记录打分分布和排序对比。

Shadow 目标是发现离线评估发现不了的问题：新模型推理延迟是否满足 SLA？打分分布是否异常（全 0 或全 1）？在线特征和训练是否一致？极端输入（全零特征、超长序列）是否导致崩溃？

Shadow 通过后进入 A/B Test。

**A/B Test（小流量实验）**。Traffic Splitter 配置实验，分配 1% 流量给新模型——真实流量，结果返回用户，影响真实体验。运行至少 24 小时观察系统指标（延迟、错误率、资源占用）。无异常后逐步放量到 5%、10%、20%，每阶段运行足够时间（通常 3 天以上）积累业务指标做统计显著性判断。

Prediction Server 承担：同时加载基线和实验模型、按请求 model_version 路由、记录每个版本调用量和打分分布。

业务指标评估：核心指标（停留时长、CTR 等）显著正向（统计显著非随机波动），辅助指标（点赞、收藏、评论）无明显负向，长期指标（留存、多样性、长尾覆盖率）平稳或提升（参考第9篇 7.2 节）。核心指标不显著或负向则回滚下线，分析原因重新训练。

**Ramp-up（逐步放量）**。A/B Test 符合预期后逐步扩大到 50%。最后确认——流量大了系统指标是否还稳定？业务指标是否保持正向？有没有小流量没发现的长尾问题？Prediction Server 持续监控新模型系统指标和打分分布。

**Full Release（全量发布）**。流量扩大到 100%，替换旧基线。全量后保留 Reverse Bucket（如 5% 流量继续跑旧模型）作长期对照——有些影响（用户留存、内容生态健康度）需很长时间才显现。旧模型在 Prediction Server 保留一段时间（如 1 周），确认无问题后卸载释放内存。新模型标记"全量上线"，更新基线配置。

**Monitor（持续监控）**。全量后持续监控业务和系统指标至少 1 周，关注长期指标变化。Prediction Server 持续上报监控数据（参考 6.4 节），发现异常及时告警。出问题通过流量切换快速回滚（参考 6.2 节）。

整个流程中，Prediction Server 的核心职责是：模型加载与版本管理、推理执行、Shadow/A/B 流量路由、监控数据上报。它不决定模型是否上线——那是算法和业务团队基于离线评估和线上实验数据做的决策——但它提供上线各阶段所需的技术支撑，让模型能安全、平稳地从离线走到全量线上。

## 8. 未来演进与总结

### 8.1 LLM 对精排的影响

大语言模型对精排的影响主要在三个层面：

**LLM 作为特征生成器**。用 LLM 生成更丰富的用户兴趣表示和内容语义表示，作为精排模型的特征输入。这是目前最成熟的方式——LLM 不直接参与在线推理，而是离线生成特征，比如用 LLM 对内容做语义理解生成主题、情感、实体等更丰富的语义特征；用 LLM 总结用户长期行为生成更抽象的兴趣表示。好处是不影响在线延迟——LLM 计算都在离线完成，在线只用生成好的特征。

**LLM 作为精排模型**。用 LLM 直接对候选打分或排序。优点是理解能力强、零样本泛化好；缺点是推理成本极高（传统模型几十到几百倍）、延迟大（几百毫秒到几秒），目前只适合小候选集或低 QPS 场景，比如对精排后 Top 20 做重排，而不是对 1000 候选做精排。

**LLM + 传统模型混合架构**。用 LLM 对少量候选做深度理解，用传统 DNN 对大量候选快速打分，两者结合兼顾效果和效率。比如传统 DNN 对 1000 候选精排选出 Top 50，再用 LLM 对这 50 个做深度理解和重排序，最终选 Top 20。这是目前最有可操作性的方案——既利用 LLM 深度理解能力，又控制了推理成本和延迟。

工程挑战：LLM 推理成本极高，需极致优化（量化、蒸馏、投机解码）才能推荐场景大规模使用；LLM 输出不确定性高，需额外校准和约束——可能给出不合理打分，需和传统模型结果融合或校验；LLM 模型更新快，需更灵活的模型管理和热更新机制。

### 8.2 召回/排序从分层优化走向联合优化

传统推荐系统中召回和精排独立优化，存在目标不一致——召回优化召回率，精排优化排序质量，但召回选出的候选不一定是精排最能排好的。比如召回选出 1000 条，但其中 800 条在精排看来分数都很低，真正高分的内容可能因召回策略局限没被选进来。

联合优化方向：

- **知识蒸馏**：将精排模型知识蒸馏到召回模型，让召回筛选出的候选就是精排打分高的内容（参考第13篇 5.1 节）。用精排对大量内容打分作软标签，训练召回模型学习"什么样的内容会被精排排在前面"。投入产出比最高的联合优化方式。
- **联合训练**：召回和精排共享底层特征表示，统一优化最终排序目标。召回用轻量分支快速筛选，精排用重型分支精准打分，两分支共享底层用户和内容表示，联合训练。从根源上保证目标一致。
- **反馈闭环**：精排打分结果反馈给召回，指导候选选择和配额分配。精排发现某类内容分数普遍高，通知召回增加这类配额；发现某路召回内容分数都低，通知减少这路配额。形成"召回→精排→反馈→召回"闭环。

联合优化可提升全链路效率，但增加系统复杂度——召回和精排不再独立，耦合在一起，调试和迭代难度增加。需在效果和可维护性间权衡，大多数团队可先从知识蒸馏做起。

### 8.3 总结

精排是推荐系统中"把候选变成排序"的核心环节，Prediction Server 是支撑精排模型在线推理的基础设施。

回顾本文：精排在召回约 1000 条候选基础上，用复杂模型和丰富特征做精准多目标预估，输出 Top 200~300；Prediction Server 作为独立无状态推理服务，包含 API 层、特征处理、模型管理、推理引擎、结果处理等模块，支持多模型共存、热更新、Batch 推理；特征获取有 Realtime Engine 传入和 Prediction Server 自取两种设计；多目标融合放在 Realtime Engine 执行——模型负责 prediction，业务层负责 objective，融合策略变化不需重新部署推理服务；通过超时降级、熔断限流、Shadow/A/B Test 支持、监控告警、特征一致性保障保证高可用；新模型上线经历 Train → Offline Eval → Registry → Shadow → A/B → Ramp-up → Full Release → Monitor 完整流程，Prediction Server 在各阶段提供技术支撑。

一句话总结：**精排与 Prediction Server，本质上是把离线训练好的复杂模型，通过高性能、高可用的在线推理服务，在毫秒级对千级候选完成精准打分，为用户提供最优的排序结果。**

精排的效果决定了推荐系统的上限——模型再准、特征再丰富，如果推理服务不稳定、延迟高，效果也交付不到用户手中。而 Prediction Server 的稳定性和性能，决定了这个上限能不能稳定地交付给用户。
